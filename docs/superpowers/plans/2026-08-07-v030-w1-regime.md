# v0.3.0 W1 — The Regime Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development` (recommended) or
> `superpowers:executing-plans` to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every gate in this repository able to fail, and remove the
mechanisms that let a test suite report success while measuring nothing.

**Architecture:** Two independent halves. The first gives the 31 remaining
inventoried gates a positive control — a known-bad input the gate must reject
and a known-good input it must accept, demonstrated in one run and recorded.
The second repairs the TypeScript suite's accountability defects, which live on
the release branch because `packages/` does not exist on `main`. Neither half
depends on the other, so they can run as parallel lanes.

**Tech Stack:** Bash, Bats, Node.js 24 test runner, TypeScript, awk, GitHub
Actions.

## Global Constraints

Every task's requirements implicitly include this section.

- **Read `plugins/foreman-qa/skills/foreman-qa/SKILL.md` and its
  `references/evidence-rules.md` before starting.** This workstream *is* that
  doctrine applied. Its central rule governs every task here: a check that
  classifies a known-bad and a known-good input identically is not coverage.
- **A positive control needs two genuinely different inputs.** Using the same
  file for `known_bad_input` and `known_good_input` produces a row that cannot
  demonstrate discrimination. This exact defect was introduced and caught in
  W0; do not reproduce it.
- Demonstrate both polarities **in the same run**, and paste the real command
  output into the evidence document. A transcript written from memory is not
  evidence.
- An unrunnable gate counts as a failure, never as a pass.
- No measurement is quoted without the command that produced it.
- `tests/positive-control-registry.tsv`, `tests/positive-control-todo.tsv`,
  `tests/baseline.tsv` and `tests/skip-budget.tsv` are **tab-separated**. Build
  rows with `printf`; never type tabs.
- Every row moved into the registry must be removed from the todo file. They
  are complementary, and `tests/lib/check-registry-compare.sh` enforces it.
- Do not weaken, skip, or delete a check to make something pass. If a gate
  cannot be given a control, record it in the todo file with a stated reason —
  "every finding fixed **or declared**" is the settled exit rule.
- Work in WSL at `/root/foreman` or a worktree under `/root/fm-wt/`. **Write
  and Edit resolve `/root/...` against Windows and create phantom files** —
  never use them on a `/root/...` path; use `wsl -e bash -lc` redirection.
- Use the Bash tool with single-quoted `wsl -e bash -lc '...'`. Keep commands
  short; long `&&` chains with nested quotes fail to parse in this environment.
- Commits carry no AI attribution and no `Co-Authored-By` trailer. Name
  explicit paths in `git add`; never `git add -A`.

## Branch placement

`main` is frozen for v0.3.0; the release branch is trunk. But the two halves
live in different places, so:

- **Tasks 1–5 (positive controls)** touch `tests/`, `env/` and `.github/`,
  all of which exist on `main`. Land them on `main` and let the next merge-down
  carry them, exactly as W0 did.
- **Tasks 6–9 (TypeScript suite defects)** touch `packages/` and
  `package.json`, which **do not exist on `main`**. They must be done on the
  release branch `agent/v029-release-artwork`.

**Never rename or delete the release branch.** Doing so closes PR #27; it
happened twice on 2026-08-07 and is recorded in `bugeventlog.md`.

### Task 1: Controls for the `tests/run.sh` gates

Start here. Three gates, in the file W0 just made trustworthy, and the one
existing worked example (`tests/run.sh::lookup_baseline`) is right beside them.

**Files:**

- Modify: `tests/positive-control-registry.tsv`
- Modify: `tests/positive-control-todo.tsv`
- Create: fixtures under `tests/fixtures/policy/`
- Create: `docs/evidence/positive-control/2026-08-08-run-sh-gates.md`

**Interfaces:**

- Consumes: the registry schema — `check_id`, `kind`, `known_bad_input`,
  `known_good_input`, `control_record`, `demonstrated_at`.
- Produces: three registry rows; `check-registry-compare.sh` still exits 0.

- [ ] **Step 1: Identify the three gates and what each actually decides**

```bash
grep "tests/run.sh" tests/positive-control-todo.tsv
```

For each, read the implementation in `tests/run.sh` and state in one sentence
what input it must reject. Do not guess from the check name — W0 twice
published a cause inferred from a name and was wrong both times.

- [ ] **Step 2: Study the one worked example before writing anything**

```bash
grep "lookup_baseline" tests/positive-control-registry.tsv
cat docs/evidence/positive-control/2026-08-07-baseline-platform.md
cat tests/fixtures/policy/baseline-platform-bad.tsv
cat tests/fixtures/policy/baseline-platform-good.tsv
```

Note the shape: the discriminator is the **table content**, not the `.bats`
file. The bad fixture omits the platform row; the good one includes it. Follow
that pattern — find the datum each gate actually reads.

- [ ] **Step 3: Build fixture pairs**

For each gate, create a known-bad and a known-good fixture that differ **only**
in the property under test. If they differ in more than one way, the control
proves nothing about which difference mattered.

- [ ] **Step 4: Demonstrate both polarities**

Run each gate against both fixtures and capture the output verbatim. Expected
shape: a NEGATIVE verdict or non-zero exit on the bad input, POSITIVE or zero
on the good one, **in the same session**.

If a gate answers identically to both, that is a finding about the gate, not a
fixture problem. Stop and report it.

- [ ] **Step 5: Record the evidence**

Create `docs/evidence/positive-control/2026-08-08-run-sh-gates.md` containing,
per gate: the command, the verbatim bad-input output, the verbatim good-input
output, and the date.

- [ ] **Step 6: Register and verify**

Append rows with `printf`, delete the matching todo rows, then:

```bash
bash tests/lib/check-registry-compare.sh
bash tests/run.sh tests/positive-control.bats
```

Expected: `positive-control: OK` and 15/15 tests passing, including test 15.

- [ ] **Step 7: Commit**

```bash
git add tests/positive-control-registry.tsv tests/positive-control-todo.tsv \
  tests/fixtures/policy docs/evidence/positive-control/2026-08-08-run-sh-gates.md
git commit -m "test(positive-control): the three tests/run.sh gates can now fail

Each carries a known-bad and known-good fixture differing only in the property
under test, with both polarities demonstrated in one run."
```

### Task 6: Establish the real TypeScript suite numbers

**On the release branch.** Before fixing anything, measure. The checkpoint says
168 bare returns; this plan's own grep found 75. Both are leads.

**Files:** Create `docs/evidence/w1/2026-08-08-ts-suite-audit.md`

- [ ] **Step 1: Count bare early returns**

```bash
grep -rEn "^\s+if \(.*\) return;" packages/*/src/*.test.ts | tee /tmp/bare-returns.txt | wc -l
```

Then read a sample. Some are legitimate capability guards that should become
explicit skips; others are dead branches. Classify, do not just count.

- [ ] **Step 2: Count anonymous skips**

```bash
grep -rEn "skip: true" packages/*/src/*.test.ts | wc -l
grep -rEn "skip: \"" packages/*/src/*.test.ts | wc -l
```

`{ skip: true }` prints a bare `# SKIP` with no reason; `{ skip: "reason" }`
prints the reason. The second form is the one that survives review.

- [ ] **Step 3: Test the glob claim by execution, not by reading**

`package.json`'s `test` script passes `packages/*/src/**/*.test.ts` patterns
**unquoted**. The claim is that `sh` lacks globstar and narrows them. But
`node --test` performs its own glob expansion, so the shell may never see them.

Settle it:

```bash
sh -c 'echo packages/core/src/**/*.test.ts'
node --test --help 2>&1 | grep -iE "glob|pattern" | head -5
```

Then prove the consequence directly: create a throwaway test at
`packages/core/src/sub/throwaway.test.ts`, run `npm test`, and check whether it
executes. Delete it afterwards. **That experiment is the finding** — the shell
semantics discussion is not.

- [ ] **Step 4: Test whether zero selection is silent**

```bash
node --test 'packages/core/src/nonexistent-*.test.ts'; echo "exit=$?"
```

Exit 0 over zero tests means a suite can silently measure nothing.

- [ ] **Step 5: Record all four findings with commands and outputs, and commit.**

## Exit criteria for W1

1. `bash tests/lib/check-registry-compare.sh` exits 0, and its printed
   `registered=` plus `deferred=` accounts for all 34 enforced checks.
2. Every deferred gate has a stated reason in
   `tests/positive-control-todo.tsv`.
3. `docs/evidence/w1/2026-08-08-regime-coverage.md` states what is covered and
   what is explicitly not, including the assertion and verdict-predicate kinds
   the comparator already excludes.
4. A test glob selecting zero files fails rather than passing.
5. No `{ skip: true }` remains in `packages/*/src/*.test.ts`; every skip states
   a reason.
6. The full suite's pass count is unchanged or higher, and any change is
   explained.
