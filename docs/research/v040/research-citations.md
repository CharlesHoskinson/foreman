# RESEARCH: Latency levers for CLI-driven LLM code audits (Foreman v0.4.0 "fast audit")

Research date: 2026-07-16. Goal: cut a 27-35 min Codex audit pass to <10 min.
All claims date-stamped; single-source claims marked UNVERIFIED. External facts only (codebase covered by another lane).

## Q1. OpenAI Codex CLI: model selection, reasoning effort, exec vs mcp-server

### Model + effort configuration

- `model` and `model_reasoning_effort` are config.toml keys; documented values for `model_reasoning_effort` are `minimal | low | medium | high | xhigh` ("xhigh is model-dependent", Responses API only). Recommended default: `medium`. [https://developers.openai.com/codex/config-reference → https://learn.chatgpt.com/docs/config-file/config-reference, accessed 2026-07-16]
- Per-invocation override works on `codex exec`: `codex -m <model> -c model_reasoning_effort="xhigh" …`. Profiles live as `$CODEX_HOME/<profile>.config.toml`, selected via `--profile <name>`; project-scoped `.codex/config.toml` is honored only for trusted projects and cannot override machine-local keys. [same config reference, accessed 2026-07-16]
- `model_reasoning_summary` accepts `auto | concise | detailed | none` (can disable reasoning summaries entirely — fewer output tokens). [same config reference, accessed 2026-07-16]
- GOTCHA: open GitHub issue reports `model_reasoning_effort` from config.toml being overridden by last-used effort on a fresh CLI launch — pass `-c model_reasoning_effort=…` explicitly in automation for reproducibility. UNVERIFIED (single source, open issue). [https://github.com/openai/codex/issues/17436, accessed 2026-07-16]

### GPT-5.6 family and effort tiers (launched 2026-07-08/09)

- GPT-5.6 ships as three tiers: **Sol** (flagship, $5/$30 per 1M in/out), **Terra** (balanced, $2.5/$15), **Luna** (fast/cheap, $1/$6); shared 1.5M-token context window. [https://www.latent.space/p/ainews-openai-launches-gpt-56-solterraluna, 2026-07-10, accessed 2026-07-16; https://codex.danielvaughan.com/2026/07/01/gpt-5-6-sol-terra-luna-codex-cli-model-selection-tiered-reasoning-cache-breakpoints/, updated 2026-07-05, accessed 2026-07-16]
- OpenAI's reasoning guide describes gpt-5.6-sol as "highest intelligence with higher latency", terra "lower cost", luna "lowest cost and latency"; effort values are model-dependent from `none…xhigh`. No quantified latency table per effort level is published. [https://developers.openai.com/api/docs/guides/reasoning, accessed 2026-07-16]
- Sol effort ladder per launch coverage: Light/Low → Medium → High → xhigh, plus **max** (more single-thread deliberation than xhigh) and **ultra** (coordinates ~4 parallel internal sub-agents; "trades higher token use for … faster time-to-result"). Confirmed across the-decoder (OpenAI staffer Vaibhav Srivastav mapping, 2026-07-10) and latent.space launch recap (2026-07-10). NOTE: `max`/`ultra` are NOT yet listed as `model_reasoning_effort` values in the official Codex config reference (ceiling there is `xhigh`) — treat max/ultra availability in Codex CLI as UNVERIFIED as of 2026-07-16. [https://the-decoder.com/openai-staffer-maps-out-which-of-gpt-5-6-sols-five-reasoning-levels-fits-which-task-complexity/, accessed 2026-07-16]

### Observed latency differences by effort

- No vendor-published latency multipliers exist: "Higher reasoning usually increases latency and credit usage, but there is no fixed cost multiplier between levels." [OpenAI reasoning guide + agiflow.io/blog/codex-model-thinking-effort-guide, accessed 2026-07-16]
- Artificial Analysis measures **GPT-5.6 Sol (xhigh): time-to-first-token ~40s** (35.8-40.0s across snapshots) vs a **2.6s median** for similar-tier reasoning models, output speed 52.4 tok/s (median 72.7). Intelligence Index: xhigh 58 vs high 56 — i.e., xhigh buys ~2 index points over high at large latency cost. [https://artificialanalysis.ai/models/gpt-5-6-sol-xhigh, accessed 2026-07-16]
- Third-party guidance (aiidelist, 2026-07-10): relative speed Low=fastest … xhigh=slow, max=very slow, ultra=variable; recommends **medium as default**, high for "trace complex behavior / subtle regressions", xhigh only for "large pull request reviews" / migration-safety work. Directionally consistent with Srivastav's mapping. [https://aiidelist.com/blog/codex-gpt-5-6-sol-reasoning-levels, accessed 2026-07-16]
- Terra/Luna speed claim: comparable results to competitors "in roughly one-third of the time" with fewer output tokens (OpenAI launch claim relayed by latent.space, 2026-07-10). UNVERIFIED against independent benchmark for audit-style tasks. [latent.space link above, accessed 2026-07-16]

### codex exec vs codex mcp-server: startup, resume, caching

- `codex exec` (non-interactive) supports: `--json` (JSONL event stream), `--output-schema <file>` (forces final message to validate against a JSON schema — fits Foreman's verdict schema), `-o <file>`, `--ephemeral` (skip writing session files), sandbox flags, and `codex exec resume <SESSION_ID>` (which also accepts `--output-schema`) for context-preserving multi-step pipelines. [https://codex.danielvaughan.com/2026/03/26/codex-cli-cicd-non-interactive/, updated 2026-07-16, accessed 2026-07-16; https://developers.openai.com/codex/noninteractive, accessed 2026-07-16 (search snippet)]
- `codex mcp-server` exposes two tools: `codex` (params: `prompt`, `model`, `config` overrides, `approval-policy`, `sandbox`, `cwd`) and `codex-reply` (params: `prompt`, `threadId`; `conversationId` is a deprecated alias). `threadId` returns in `structuredContent.threadId` and persists across turns "without reinitializing the environment"; server supports long sessions (`client_session_timeout_seconds=360000`). [https://learn.chatgpt.com/docs/mcp-server, accessed 2026-07-16]
- Sessions persist in `~/.codex/state.db`; thread IDs remain valid across reconnections; a fix landed so `codex-reply` rehydrates threads from disk when not in memory. [https://github.com/openai/codex/issues/12596, accessed 2026-07-16]
- **No published number for codex process startup overhead** (exec cold-start vs warm mcp-server). UNVERIFIED — but structurally: mcp-server + `codex-reply` avoids re-spawning the agent and re-exploring the repo; separate `codex exec` runs can still hit the server-side prompt cache if the prefix is stable (see Q5). [inference from sources above]
- Context caching: GPT-5.6 introduces explicit cache breakpoints with a **guaranteed 30-minute minimum prefix-cache life** (writes 1.25x, reads -90%); OpenAI prompt-caching docs confirm "at least 30 minutes" retention for GPT-5.6+, 1024-token minimum, cross-request reuse via prefix hash routing + `prompt_cache_key`. So repeated audit runs within 30 min sharing a stable system-prompt/tool-def prefix get cheap+faster prefill even across separate `codex exec` invocations. [https://developers.openai.com/api/docs/guides/prompt-caching, accessed 2026-07-16; danielvaughan 2026-07-01 article, accessed 2026-07-16]

## Q2. Parallel audit patterns (shard + consolidate)

- **Shard-by-concern is the dominant published pattern.** HAMY (2026-02-20) runs 9 parallel subagents each on one quality dimension (security, performance, test quality, deps, simplification, …) over the same diff, then a consolidation phase produces one severity-ranked summary; author reports ~75% of findings useful vs <50% with a monolithic review — parallelism raised precision, wall-clock not disclosed. [https://hamy.xyz/blog/2026-02_code-reviews-claude-subagents, accessed 2026-07-16]
- Anthropic's Claude Code PR-review feature (March 2026) uses the same shape: multiple agents attack the PR from different angles (logic, security, edge cases, performance), a final agent consolidates, ranks, and filters. Shareuhack's /ultrareview writeup adds a verification twist: only surface findings **independently reproduced** by more than one agent — a precision filter that costs recall. [https://www.pravin.solutions/posts/claude-code-pr-review-agents-agentic-ai-developer-tools-2026, accessed 2026-07-16; https://www.shareuhack.com/en/posts/claude-code-pr-review-subagents-guide, accessed 2026-07-16]
- **Shard-by-file/directory** appears in fan-out guides: "one analyzer per directory … cutting a 12-minute serial scan to 90 seconds" (skills-hub, May 2026). UNVERIFIED (single source, marketing-adjacent), but the ~Nx speedup from parallel fan-out is mechanically sound and matches OpenAI's documented parallelization lever (Q5). [https://skills-hub.ai/blog/claude-code-subagents-2026, accessed 2026-07-16]
- Consolidation strategy (MindStudio, Apr 2026): dedupe, boost findings flagged by 2+ agents, flag contradictions, output one prioritized review. [https://www.mindstudio.ai/blog/automated-code-review-multiple-ai-agents, accessed 2026-07-16]
- Commercial evidence on precision/recall tradeoff: Greptile (parallel agents + codebase graph) posts the higher catch rates but with heavy noise — 82% catch claim with 30-50% of findings needing manual triage on large repos; 11 FPs/run vs CodeRabbit's 2 in one benchmark. Tenki's May-2026 benchmark (50 PRs, 122 real bugs, 3-LLM-judge): Tenki 68.9% catch/F1 41.7; Greptile 36.1%/22.1; CodeRabbit 28.7%/26.7; Copilot 24.6%/21.4; agents (Devin 36%, Cursor 32%) had higher precision. Takeaway: more parallel breadth raises recall and false positives; a consolidation/verification stage is what protects precision. [https://tenki.cloud/benchmarks/code-reviewer, updated 2026-05-20, accessed 2026-07-16; https://www.augmentcode.com/tools/coderabbit-vs-greptile-vs-augment-cosmos, accessed 2026-07-16]

## Q3. xAI Grok CLI ("Grok Build") as third audit vendor

- Headless invocation: `grok -p "<prompt>"` with `--output-format plain | json | streaming-json` (json = one final object; streaming-json = NDJSON events); `-m/--model`, `--cwd`, `--always-approve`; sessions: `-s/--session-id` (create/resume named headless session), `-r/--resume <ID>`, `-c/--continue`. Headless JSON now includes token usage + cost per prompt/session (release note 2026-07-11). [https://docs.x.ai/build/cli/headless-scripting, accessed 2026-07-16; https://releasebot.io/updates/xai/grok-build, accessed 2026-07-16]
- Reasoning effort: `--effort` / `--reasoning-effort` flags are interchangeable (release note 2026-07-07); per-model effort menus configurable via config.toml (2026-07-05); effort used is recorded in summary.json. Exact tier names per model not published on the headless page — UNVERIFIED detail. [releasebot.io + docs.x.ai, accessed 2026-07-16]
- Current flagship: **grok-4.5** ("the same model that powers Grok Build", available on the xAI API). One secondary source still cites grok-4.3 as flagship — go with xAI's own docs (grok-4.5). [https://docs.x.ai/build/overview, accessed 2026-07-16]
- Structured output: xAI **API** supports `response_format: json_schema` (Draft 2020-12/Draft-07 subset; grok-4.5 named in examples; tool-call args always strict-schema). The **CLI's** `--output-format json` is an envelope format, not a user-schema-forced verdict — no documented CLI equivalent of Codex's `--output-schema` as of 2026-07-16 (gap: schema enforcement would need a post-validation step or direct API call). [https://docs.x.ai/developers/model-capabilities/text/structured-outputs, accessed 2026-07-16]

## Q4. Google Gemini CLI as auditor

- Headless: `-p/--prompt` (or non-TTY) triggers headless mode; `--output-format json` returns `{response, stats (tokens + API latency), error}`; `--output-format stream-json` emits NDJSON events (`init`, `message`, `tool_use`, `tool_result`, `error`, `result`). Exit codes: 0 ok, 1 error, 42 input validation, 53 turn-limit. [https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/headless.md, accessed 2026-07-16]
- Model lineup (July 2026): Gemini 3 Pro + Gemini 3 Flash generally available to paid tiers; **Gemini 3.1 Pro** rolling out (`gemini -m gemini-3.1-pro-preview`); default is auto-routing ("Auto (Gemini 3)": simple → 2.5 Flash, complex → 3 Pro; "Pro" routing forces most-capable). For deterministic audit latency, pin `-m` rather than trusting the router. [https://geminicli.com/docs/get-started/gemini-3/, accessed 2026-07-16; https://developers.googleblog.com/gemini-3-flash-is-now-available-in-gemini-cli/, accessed 2026-07-16]
- Thinking control: Gemini 3 **API** exposes `thinking_level` = `minimal | low | medium | high` (relative allowances, not token guarantees; mutually exclusive with legacy `thinking_budget`). **No documented CLI flag** for thinking level in gemini-cli headless docs as of 2026-07-16 — configurable only if the CLI surfaces model config in settings.json (UNVERIFIED). [https://ai.google.dev/gemini-api/docs/interactions/gemini-3, accessed 2026-07-16]
- Structured output: no schema-forced final-answer flag documented for gemini-cli headless (JSON envelope only) — same gap as Grok CLI. [gemini-cli headless.md, accessed 2026-07-16]

## Q5. Prompt-side latency levers (documented)

- **Output tokens dominate**: OpenAI's latency guide: "Cutting 50% of your output tokens may cut ~50% your latency," while "cutting 50% of your prompt may only result in 1-5% latency improvement." Reasoning tokens are output tokens — this is why effort level is the single biggest dial. [https://developers.openai.com/api/docs/guides/latency-optimization, accessed 2026-07-16]
- **Fewer requests/round-trips** is an explicitly documented lever: each request adds round-trip latency; merge sequential steps into one prompt. For an agentic auditor, every tool call = one full model turn (decode reasoning + emit call + re-prefill grown context). Pre-packaging the diff/context so the auditor makes zero-to-few tool calls converts an N-turn loop into ~1 turn. [same OpenAI guide, accessed 2026-07-16]
- **Harness overhead quantified** (UW SyFI TraceLab, 253k Codex tool calls): end-to-end tool time 418.1h vs 341.5h internal execution → **~19% residual harness overhead**, avg 1.11s/call, P50 0.13s / P90 0.24s / P99 10.0s; `exec_command` dominates residual (64.1h), attributed largely to approval workflow. Implication: read-only sandbox + no-approval policy + fewer tool calls all cut real seconds. [https://tracelab.cs.washington.edu/exp/tool_calls/codex_wall_internal_gap/, accessed 2026-07-16]
- **Prefill/TTFT vs context size**: longer prompts increase TTFT (full-sequence KV-cache build before generation); prompt caching makes TTFT near-constant on repeated prefixes ("reducing latency by two orders of magnitude under long inputs" in agentic multiturn workloads — research claim). OpenAI: cache eligibility ≥1024 tokens; GPT-5.6+ guarantees ≥30-min prefix cache; `prompt_cache_key` improves hit routing. Anthropic/Redis-style guides agree directionally. [https://redis.io/blog/what-is-prompt-caching/, accessed 2026-07-16; https://developers.openai.com/api/docs/guides/prompt-caching, accessed 2026-07-16; https://www.elvex.com/blog/reduce-llm-prefill-latency-multi-million-token-inputs, accessed 2026-07-16]
- **Measured TTFT at xhigh** (includes thinking): GPT-5.6 Sol xhigh TTFT ~40s vs 2.6s tier median — reasoning effort, not prefill, is the dominant TTFT term at high effort. [https://artificialanalysis.ai/models/gpt-5-6-sol-xhigh, accessed 2026-07-16]
- **Parallelization** is a first-class documented lever (run non-dependent steps simultaneously; speculative execution for sequential ones). [OpenAI latency guide, accessed 2026-07-16]

### Sanity math for the <10 min target
27-35 min today at Sol/xhigh single-lane. Lever 1 (xhigh→high) plausibly 1.5-2.5x; lever 2 (3-4 parallel shards + consolidate) another ~2-3x on the residual; levers 3+4 shave turn count and output tokens. Combined 4-6x is credible → 5-9 min. No single lever gets there alone; 1+2 together are the core of the plan.
