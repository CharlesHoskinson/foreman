# REPORT_process.md — Lane C: Bun.spawn Windows process semantics, Bun Shell, bun test (Foreman v0.2.5)

VERDICT: **GO-WITH-CAUTIONS** — Bun.spawn is acceptable as the child-spawn layer for vendor CLIs on Windows (it is a thin wrapper over libuv `uv_spawn`, with timeout/killSignal/maxBuffer/AbortSignal built in), BUT (a) `.kill()` is TerminateProcess of the **direct child only** — process-**tree** kill and Job-Object ownership must be done by the launcher via FFI/`taskkill`; (b) graceful shutdown via CTRL_BREAK (`GenerateConsoleCtrlEvent`) has **no built-in** — FFI only, and it is incompatible with `detached: true` (DETACHED_PROCESS strips the console); (c) **CREATE_SUSPENDED / raw creation flags are not exposed**, so if Job-Object assignment must be race-free (assign-before-first-instruction), the spawn must go through FFI `CreateProcessW(CREATE_SUSPENDED)` instead of Bun.spawn; assigning the PID to a Job immediately after Bun.spawn returns is the pragmatic near-equivalent (small race window). Bun Shell and bun test are mature enough for the launcher's needs, with listed caveats.

Research date: 2026-07-16. Bun stable line at research time: v1.3.x (fake timers landed v1.3.4, Dec 2025; v1.3.14 shipped 70+ Bun Shell bug fixes).

---

## 1. Bun.spawn on Windows — exact semantics

**Implementation substrate.** On Windows, Bun spawns processes through **libuv `uv_spawn`** (bindings in `src/deps/libuv.zig`, called from `src/bun.js/api/bun/process.zig` — crash stacks show `libuv.zig: spawn` → `process.zig: spawnProcess` → libuv `process.c: uv_spawn`). Therefore libuv's Windows process model is the ground truth for kill/detach/exit-code behavior. [https://github.com/oven-sh/bun/blob/main/src/deps/libuv.zig, accessed 2026-07-16; https://docs.libuv.org/en/v1.x/process.html, accessed 2026-07-16]

**Options surface (from the API reference `SpawnOptions`)** [https://bun.com/reference/bun/spawn, accessed 2026-07-16]:
`cmd, cwd, env, stdin/stdout/stderr, stdio, onExit, ipc, onDisconnect, serialization ('json'|'advanced'), windowsHide, windowsVerbatimArguments, argv0, signal (AbortSignal), timeout, killSignal, maxBuffer, detached, lazy, terminal`.

- **timeout**: "The maximum amount of time the process is allowed to run in milliseconds." Built-in; added in **Bun v1.2.6** (2025-03-25). On expiry the process is killed with `killSignal` (default SIGTERM → TerminateProcess on Windows). [https://bun.com/blog/bun-v1.2.6, accessed 2026-07-16; https://bun.com/docs/api/spawn, accessed 2026-07-16]
- **killSignal**: "The signal to use when killing the process after a timeout, when the AbortSignal is aborted, or when the process goes over the `maxBuffer` limit." Accepts name or number. [https://bun.com/reference/bun/spawn, accessed 2026-07-16]
- **maxBuffer**: max bytes the process may output; exceeding it kills the child with `killSignal`. (Note: this is a kill-trigger, not a truncation — useful as a runaway-output guard.) [same ref]
- **signal**: AbortSignal aborts the subprocess. [same ref]
- **windowsHide**: hidden window (libuv `UV_PROCESS_WINDOWS_HIDE`). **windowsVerbatimArguments**: "no quoting or escaping of arguments is done on Windows" (libuv `UV_PROCESS_WINDOWS_VERBATIM_ARGUMENTS`) — both present and map 1:1 to libuv flags. [https://bun.com/reference/bun/spawn; https://github.com/oven-sh/bun/blob/main/src/deps/libuv.zig, accessed 2026-07-16]
- **detached**: present (`detached?: boolean`, was long undocumented in types — issue #11922). On POSIX → `setsid()`; on Windows → libuv `UV_PROCESS_DETACHED`, i.e. creation flags `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`: child is a process-group leader, survives parent exit, and is **not** put in libuv's kill-on-close job. Combine with `proc.unref()` and `stdio: ["ignore","ignore","ignore"]` to fully let go. [https://bun.com/reference/bun/Spawn/SpawnOptions/detached, accessed 2026-07-16; https://github.com/oven-sh/bun/issues/11922, accessed 2026-07-16; https://docs.libuv.org/en/v1.x/process.html ("make it a process group leader … keep running after the parent exits"), accessed 2026-07-16]
- **CREATE_SUSPENDED / raw creation flags: ABSENT — confirmed.** No creation-flags option exists anywhere in `SpawnOptions` (checked the full reference interface) and libuv itself does not expose arbitrary `dwCreationFlags`. The only flag-adjacent knobs are `windowsHide`, `windowsVerbatimArguments`, `detached`. **Consequence: a suspended start (for race-free Job-Object assignment before the child runs) requires FFI `CreateProcessW` with `CREATE_SUSPENDED` + `ResumeThread`, outside Bun.spawn.** [https://bun.com/reference/bun/spawn, accessed 2026-07-16]

**.kill() semantics on Windows.** `proc.kill()` / `proc.kill(sig)` goes to libuv `uv_process_kill`. On Windows libuv emulates signals: any terminating signal (SIGTERM/SIGKILL/SIGINT/number) → **`TerminateProcess` of the direct child only**; signal 0 is a liveness probe. **There is no tree-kill** — grandchildren survive. Multiple Bun issues document orphaned descendants (`--watch` leaving spawned servers alive #7440/#13539, children surviving on CI #11892). libuv fakes `term_signal` in the exit callback for processes it killed, so Bun's `signalCode` will read e.g. `"SIGTERM"` even though no POSIX signal existed. [https://docs.libuv.org/en/v1.x/process.html, accessed 2026-07-16; https://github.com/oven-sh/bun/issues/7440, https://github.com/oven-sh/bun/issues/13539, https://github.com/oven-sh/bun/issues/11892, accessed 2026-07-16]

**Implicit Job Object (important, easy to miss).** libuv on Windows assigns every **non-detached** child to a process-wide job object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` + `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`. Net effect: direct children die when the Bun launcher process dies, but **grandchildren silently break away** and are NOT covered (this is deliberate libuv behavior; see libuv#3179 questioning SILENT_BREAKAWAY_OK). So Bun.spawn gives you parent-death cleanup for depth-1 only. Since Windows 8, jobs nest, so the launcher can additionally assign the child's PID to its **own** Job Object (without silent-breakaway) to capture the whole tree. [https://github.com/libuv/libuv/issues/3179, accessed 2026-07-16; https://github.com/libuv/libuv/blob/v1.x/src/win/process.c, accessed 2026-07-16]

**Exit-code fidelity.** libuv reports `exit_status` as `int64_t` taken from `GetExitCodeProcess`, so the full 32-bit DWORD — including NTSTATUS values like 3221225477 (0xC0000005) and 3221225786 (0xC000013A, console closed) — passes through un-truncated; Node on the same substrate reports these values verbatim. Bun's `Subprocess.exitCode` is `number | null` with no documented masking. **[UNVERIFIED at Bun layer: I found no Bun issue/doc explicitly showing a >2^31 NTSTATUS in `exitCode`; libuv passthrough makes truncation unlikely, but the launcher should log `exitCode` raw and treat >=0x80000000 (or >255) as "abnormal Windows termination" — verify once empirically in the spike.]** Exit info surface: `exitCode`, `signalCode`, `exited` (Promise), `killed`. [https://docs.libuv.org/en/v1.x/process.html (`uv_exit_cb(…, int64_t exit_status, int term_signal)`), accessed 2026-07-16; https://bun.com/reference/bun/Subprocess/exitCode, accessed 2026-07-16]

**Bonus surface**: `SpawnOptions.terminal` exists (ConPTY-backed `Bun.Terminal`, new in the 1.3 line). Windows caveat from docs: on Windows < 11 24H2 (build 26100), `ClosePseudoConsole` can block until conhost flushes, so `terminal.close()` may not terminate a still-running child promptly — kill the child first. Also open bug: writing `\x03` via `Terminal.write()` does not generate SIGINT for the foreground process (#25832/#25779). Do not rely on Bun.Terminal for graceful-interrupt delivery yet. [https://bun.com/reference/bun/spawn, accessed 2026-07-16; https://github.com/oven-sh/bun/issues/25832, https://github.com/oven-sh/bun/issues/25779, accessed 2026-07-16]

## 2. stdout/stderr byte counting for heartbeats

**Yes — streaming without whole-output buffering is the native model.** With `stdout: "pipe"`, `proc.stdout` is a `ReadableStream<Uint8Array>`; iterate `for await (const chunk of proc.stdout) { bytes += chunk.byteLength; lastActivity = now(); forward(chunk); }`. Backpressure is the OS pipe buffer plus pull-based reads — chunks arrive as the child flushes, nothing accumulates unless you use the buffering helpers (`Bun.readableStreamToText`, `proc.stdout.text()` etc. — avoid those for long-running children). `stderr` **defaults to `"inherit"`** — must be set to `"pipe"` explicitly if you want to count/heartbeat it. [https://bun.com/docs/api/spawn, accessed 2026-07-16]

**Known Windows pipe hazards (ranked by relevance to the launcher):**
- **#15564** — on Windows, with `stderr: "pipe"` but stdout NOT piped, stderr arrives **garbled/corrupted**. Confirmed bug, was open as of the issue page fetched today; mitigation: always pipe stdout and stderr together (the launcher does anyway). **[status "still open in mid-2026" UNVERIFIED — page fetch showed open/assigned, no fix PR linked]** [https://github.com/oven-sh/bun/issues/15564, accessed 2026-07-16]
- **#33020** — Windows: parent never exits after child dies when **stdin is an async iterable** (stream pump promise never settles, event loop stays referenced). Mitigation: feed stdin via `FileSink` (`proc.stdin.write()/end()`) or a plain ReadableStream, not an async iterable. Recent (≈3 weeks old). [https://github.com/oven-sh/bun/issues/33020, accessed 2026-07-16]
- **#24690** — `Bun.spawn` with `stdout: "pipe"` returns **empty output when run inside `bun test`** (works outside). Open as of fetch (reported on macOS, plausibly cross-platform). Directly threatens launcher **unit tests** that spawn real processes — prefer mocking the spawn layer or run spawn-integration tests as plain `bun run` scripts, not inside `bun test`. [https://github.com/oven-sh/bun/issues/24690, accessed 2026-07-16]
- Historical stream-stall bugs (#1320 "stops reading after first chunk", #11297 "pipe file stream hangs") are old and fixed-era, but they justify a watchdog: if child is alive and 0 bytes arrive for N minutes, treat as hang. [https://github.com/oven-sh/bun/issues/1320, https://github.com/oven-sh/bun/issues/11297, accessed 2026-07-16]

## 3. Bun Shell ($) — Windows maturity

- **Own interpreter, not cmd/bash — confirmed.** Docs: "By design, Bun Shell does not invoke a system shell like `/bin/sh`. It's a re-implementation of bash that runs in the same Bun process" — "a small programming language … with a handwritten lexer, parser, and interpreter", and "Bun Shell scripts are cross-platform, so they work on Windows." [https://bun.com/docs/runtime/shell, accessed 2026-07-16]
- **Coverage**: pipes `|`, full redirection set (`<`, `>`, `>>`, `2>`, `2>>`, `&>`, `&>>`, `2>&1`, `1>&2`), native globs (`**`, `*`, `{a,b}` expansion), env vars, command substitution `$(...)`, `&&`/`||`/`;`, built-ins (`cd`, `rm`, `echo`, …), and **subshells** (added when npm lifecycle scripts on Windows needed them). [https://bun.com/docs/runtime/shell, accessed 2026-07-16; https://bun.com/blog/bun-v1.1.1, accessed 2026-07-16]
- **Maturity signal**: v1.3.14 fixed **70+ Bun Shell bugs** in one release — active hardening, but also evidence the interpreter still had many edge-case bugs into 2026 (past Windows items: `rm -rf` failures #13523, `cd` hang on odd errno). [https://bun.com/blog/bun-v1.3.14, accessed 2026-07-16; https://github.com/oven-sh/bun/issues/13523, accessed 2026-07-16]
- **Process control gap**: no `.kill()` on a running `$` command; backgrounding/job control absent (enhancement #11868 still open). Do NOT use `$` for the vendor-CLI lane (no kill, no streaming heartbeat control) — Bun.spawn only. [https://github.com/oven-sh/bun/issues/11868, accessed 2026-07-16]
- **Verdict (informational)**: suitable *later* for replacing short harness bash scripts (copy/glob/env/pipe workloads) on Windows; not suitable for long-running supervised processes.

## 4. bun test — enough for launcher unit tests?

**Yes, with one integration-test caveat (#24690 above).**
- **JUnit**: `bun test --reporter=junit --reporter-outfile=junit.xml` (also `[test.reporter] junit = "path"` in bunfig.toml); shipped in v1.1.35; XML includes environment properties for CI. Reporters available: `default`, `dot`, `junit`, `only-failures`. **TAP: not supported** (no TAP reporter exists). GitHub Actions annotations are emitted automatically when CI is detected. [https://bun.com/docs/test/reporters, accessed 2026-07-16; https://bun.com/blog/bun-v1.1.35, accessed 2026-07-16]
- **Watch-free CI mode**: `bun test` runs once by default (watch is opt-in via `--watch`); `--bail`, per-test `--timeout`, `--rerun-each` available — CI-friendly out of the box. [https://bun.com/docs/test/reporters + bun test CLI docs, accessed 2026-07-16]
- **Fake timers**: landed **v1.3.4 (2025-12-06)** — `jest.useFakeTimers({now})`, `advanceTimersByTime`, `advanceTimersToNextTimer`, `runAllTimers`, `runOnlyPendingTimers`, `clearAllTimers`, `getTimerCount`, `isFakeTimers`, `useRealTimers`, plus `setSystemTime`. Fresh (7 months old at research time); one ecosystem-integration bug reported (#26284 with testing-library/react — irrelevant to launcher). Good enough for testing heartbeat/timeout logic. [https://bun.com/blog/bun-v1.3.4, accessed 2026-07-16; https://bun.com/reference/bun/test/jest/useFakeTimers, accessed 2026-07-16; https://github.com/oven-sh/bun/issues/26284, accessed 2026-07-16]

## 5. Signals / console events on Windows

- **Sending CTRL_BREAK to a child: no built-in — confirmed by absence.** Neither Bun.spawn/Subprocess.kill nor `node:child_process` in Bun exposes `GenerateConsoleCtrlEvent`; libuv's kill path is TerminateProcess-only. Graceful interrupt therefore requires **`bun:ffi` → kernel32 `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, childPgid)`**, and it only reaches processes that **share a console** with the caller and were spawned with `CREATE_NEW_PROCESS_GROUP`. Critical interaction: Bun's `detached: true` sets `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` — DETACHED_PROCESS gives the child **no console at all**, so CTRL_BREAK can never be delivered to a detached child. There is no Bun.spawn combination that yields "same console + new process group". [https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent, accessed 2026-07-16; https://docs.libuv.org/en/v1.x/process.html, accessed 2026-07-16]
- **Bun receiving CTRL_C**: `process.on("SIGINT", handler)` is supported and documented (handler must call `process.exit()` itself). SIGBREAK handling on Windows should follow the libuv/Node mapping (Ctrl+Break → 'SIGBREAK') — **[UNVERIFIED in Bun docs specifically]**. Known Windows wrinkles: SIGINT handlers can be skipped/truncated when the script is run via `bun run <script>` wrappers or `--filter` (#15878, #24360, #11400, #20319) — run the launcher entrypoint as `bun path/to/launcher.ts` directly, not through a package.json script, if graceful Ctrl+C matters. [https://bun.com/docs/guides/process/ctrl-c, accessed 2026-07-16; https://github.com/oven-sh/bun/issues/15878, https://github.com/oven-sh/bun/issues/24360, https://github.com/oven-sh/bun/issues/11400, https://github.com/oven-sh/bun/issues/20319, accessed 2026-07-16]

## RISKS (ranked)

1. **Tree-kill gap (HIGH).** `.kill()`/timeout/AbortSignal/maxBuffer all TerminateProcess the direct child only; vendor CLIs (npm-shim → node → …) are trees. Without launcher-owned Job Objects (or `taskkill /T /F` fallback), timeouts leak grandchildren that hold pipes/ports. libuv's own job covers launcher-death only, depth-1 only (SILENT_BREAKAWAY_OK).
2. **No graceful-shutdown channel via Bun.spawn (HIGH for "polite stop, then kill" designs).** killSignal is cosmetic on Windows (everything is TerminateProcess). CTRL_BREAK needs FFI *and* CREATE_NEW_PROCESS_GROUP *without* DETACHED_PROCESS, which Bun.spawn cannot produce → the graceful lane needs FFI CreateProcessW, or accept hard-kill-only.
3. **`bun test` + Bun.spawn stdout capture bug #24690 (MEDIUM).** Spawn-integration tests inside `bun test` may capture empty stdout. Mitigate: mock spawn layer in unit tests; run real-spawn smoke tests as standalone scripts.
4. **Windows piped-stderr corruption #15564 (MEDIUM, easy mitigation).** Always pipe stdout and stderr together.
5. **Async-iterable stdin hang #33020 (MEDIUM).** Never feed stdin via async iterable on Windows; use FileSink writes.
6. **Exit-code NTSTATUS fidelity UNVERIFIED at Bun layer (LOW).** Verify empirically; log raw DWORD.
7. **Fake timers are 7 months old (LOW).** Fresh implementation; keep timer-logic tests simple.
8. **Bun Shell still shedding bugs in bulk (LOW; informational lane only).** 70+ fixes in v1.3.14 alone — fine for scripts, not for supervision.

## Spawn design consequence (FFI vs Bun.spawn)

**Bun.spawn safely covers:** launching vendor CLIs (`cmd` array, `cwd`, `env`, `argv0`, `windowsHide: true`, `windowsVerbatimArguments` when needed); piped stdout+stderr streaming with per-chunk byte counting for heartbeats; built-in `timeout` + `maxBuffer` + AbortSignal as coarse runaway guards; `exitCode`/`exited` for completion; `detached + unref` for fire-and-forget helpers (accepting no console → no CTRL_BREAK ever).

**The launcher must add via FFI (kernel32 through `bun:ffi`) or external tools:**
1. **Job Object per child**: `CreateJobObjectW` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (no silent-breakaway) + `AssignProcessToJobObject(hJob, OpenProcess(pid))` immediately after Bun.spawn returns. Nested jobs (Win8+) make this coexist with libuv's internal job. Kill = `TerminateJobObject` → true tree kill; launcher crash → OS reaps the tree. Residual risk: the child can spawn a grandchild in the microseconds before assignment — acceptable for vendor CLIs, or eliminated by option 3.
2. **Graceful interrupt (optional lane)**: `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, pid)` — requires the child spawned with `CREATE_NEW_PROCESS_GROUP` and a shared console; Bun.spawn cannot set that flag alone, so this lane also needs FFI CreateProcessW. If skipped: document that Windows stop = hard TerminateJobObject after a cooperative-shutdown request over stdin/IPC instead.
3. **Race-free assignment (only if required)**: FFI `CreateProcessW(CREATE_SUSPENDED | CREATE_NEW_PROCESS_GROUP)` → `AssignProcessToJobObject` → `ResumeThread`, wiring the three pipe handles manually — full replacement of Bun.spawn for the supervised lane. Recommended posture for v0.2.5: **Bun.spawn + immediate Job assignment (option 1), with `taskkill /PID n /T /F` as a zero-FFI fallback**, deferring option 3 unless the assignment race is observed to matter.
