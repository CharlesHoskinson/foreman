# Foreman orchestration options for a Windows-hosted multi-agent coding harness

## Executive summary

The strongest recommendation is **to keep Foreman’s orchestration core in-house, but stop relying on Bash to be the process owner**. In practice that means adopting a **small native Windows launcher built around Job Objects**, plus a **real local queue/supervisor such as pueue** for admission control and recovery metadata, while preserving Foreman’s emerging **event log + git checkpoint** architecture. This path is the only one that directly addresses the worst current failures—especially unreaped subprocesses and wrappers that “finish” while a child CLI still runs—*by construction* on the actual host you have: Windows 11, Git Bash, no Docker requirement, and unstable WSL under load. Microsoft’s Job Objects can terminate *all* associated processes when the last job handle closes by using `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which is exactly the primitive your current timeout/wrapper stack is missing. Pueue already gives you persisted queues, logs, groups, per-group parallelism, restart/kill controls, JSON status, and crash recovery on Windows, without demanding a server cluster or a Linux runtime. citeturn17search1turn17search3turn16view0

The best runner-up is **Prefect**, but only as an **adaptation target**, not as a drop-in replacement. Prefect now documents first-class Windows support, can run a local server with SQLite by default, and has workers/work pools that would give Foreman a cleaner state model and UI. But Prefect does **not** make arbitrary vendor CLIs safe on its own; you would still need the same native launcher to ensure process-group ownership and hard kill semantics. So Prefect is attractive if you want to move the orchestrator from Bash into Python over the next quarter, not if you need the fastest path to eliminating F1 and F2. citeturn13search10turn13search4turn13search0

The higher-complexity long-term option is **Temporal**, again as an adaptation target rather than a direct replacement. Temporal is the most mature durable-execution model in this group, but the official material I found is much more comfortable with local/dev workflows and Linux/Kubernetes-style deployments than with your “single Windows host, no Docker, bash-first” operating model. More importantly, Temporal still would not own the vendor CLI process tree for you; you would need a Windows-native activity launcher anyway. That makes Temporal strategically appealing if Foreman later becomes a multi-host, multi-developer platform, but overkill for the next 90 days. citeturn1search15turn4search0turn4search1

A decisive theme emerged from the research: **most workflow engines solve durable state better than they solve OS-process ownership**. Foreman’s worst incidents are not primarily “agent orchestration” bugs; they are **subprocess supervision bugs**. For that reason, the winning plan is not to replace Foreman wholesale with an AI-agent framework or a data orchestrator. It is to **use the right primitive for the dangerous layer**—Windows Job Objects for child ownership, explicit lane heartbeats/state transitions, per-vendor config-dir isolation, and queue-aware admission control—then keep Foreman’s event log/checkpoint model as the source of truth. citeturn17search1turn17search3turn16view0turn34search5turn34search7

## Candidate assessments

### Hardened Foreman with Windows Job Objects and pueue

This is the best fit for the problem you actually have. Microsoft’s Job Objects let a parent associate a launched process with a job and apply limits to the entire tree; with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, closing the last handle kills all associated processes. That gives you the missing invariant Bash and GNU `timeout` did not provide. GNU `timeout` is also a weaker answer on its own: the man page warns that in `--foreground` mode, children of the command will **not** be timed out, and although coreutils 9.10 improved signal propagation, that still does not give you Windows-native tree ownership. On this host class, the safe design is a tiny launcher—Rust, Go, or .NET are all fine—that creates a Job Object, spawns the vendor CLI as its child, forwards stdio, emits heartbeats, and on timeout performs a graded stop: cancel/CTRL_BREAK if available, then close the job handle, then fall back to terminate. citeturn17search1turn17search3turn18search1turn18search3

Pueue complements that launcher unusually well. Its daemon persists the queue and logs to disk, restores them after crashes, supports multiple groups with independent parallelism, can kill/restart/pause tasks, and offers JSON status output. It also explicitly says Windows is fully supported, with prebuilt Windows binaries on each release. The catch is equally clear in its own README: pueue is intentionally **not** a heavy-duty distributed programmable scheduler and is designed for a single user with simple architecture. That is a feature, not a bug, for Foreman today. It means you can use pueue for **lane admission control**—including “at most one xAI lane per account/profile” if the CLI serializes internally—without importing a cluster-shaped problem. citeturn16view0

Integration effort is moderate and bounded: around **12–18 developer-days** for a strong first version. A realistic breakdown is 2–3 days for the native launcher, 2–3 days for event schema and state transitions, 2 days for pueue group integration, 2–3 days for watchdog/heartbeat logic, 2–4 days for checkpoint/resume wiring, and 2–3 days of destructive testing across Grok/Codex/Claude lanes. License posture is excellent: pueue is Apache-2.0 and MIT dual-licensed, with active maintenance and a March 2026 release. citeturn16view0

### Prefect

Prefect is the best “full orchestrator” if you want native Windows support and a real control plane without immediately taking on Temporal-class complexity. Prefect’s current docs explicitly describe running Prefect server and workers on Windows with PowerShell, and its self-hosted local server defaults to a SQLite database at `~/.prefect/prefect.db`. Workers poll work pools and execute scheduled runs, which maps cleanly onto Foreman’s architect-dispatcher model. Prefect also has current release activity through mid-2026. citeturn13search10turn13search4turn13search0turn13search8

The limitation is structural: Prefect orchestrates *runs* well, but Foreman needs safe orchestration of **arbitrary CLI subprocess trees**. You can absolutely wrap each lane as a Prefect task or flow run, store state in Prefect, and gain a better UI and retry model; however, Prefect does not magically prevent orphaned Grok or Codex children. Your lane runner would still need the same native process launcher and heartbeat protocol. In other words, Prefect helps with F4 and F5 immediately, but only helps with F1 and F2 if you also implement the same low-level hardening you need for the in-house path. citeturn13search0turn13search12turn17search1

Migration cost is therefore meaningfully higher than “just harden Foreman”: about **20–35 developer-days**. Most of that cost is not installing Prefect. It is rewriting Bash-centric dispatch/resume behavior into Python flows and tasks, mapping lane state into Prefect run state, adding the native launcher as a task wrapper, and moving event-log semantics into Prefect-compatible metadata and artifacts. Prefect remains a very good second choice if you want a cleaner operator experience and are willing to leave Bash as the control plane. citeturn13search0turn13search3turn13search15

### Temporal

Temporal remains the benchmark for durable execution. Its model is built around persisted workflow state and retryable activities, making it an obvious candidate whenever “resume after crash” and “don’t lose progress” are central concerns. For Foreman’s F5 and future checkpoint/replay goals, Temporal’s approach is fundamentally aligned with where you are already heading conceptually: append-only history, replay, and resumability. That is why it remains the best long-term platform candidate if Foreman grows into a more general orchestration service. citeturn1search15turn4search0turn4search1

But Temporal is not the right first move here. The official material I found supports local development with the Temporal CLI dev server and emphasizes production deployment patterns that are more Linux/Kubernetes-shaped than “Windows 11 + Git Bash + no Docker by default.” More importantly, the activity worker that launches Grok/Codex/Claude would still need to own and reap the subprocess tree correctly. So Temporal would improve F4/F5/F6-style durability and history semantics, while leaving the F1/F2 danger zone to your own launcher anyway. On your current host and staffing model, that means you would be paying high migration/ops cost before fixing the failures that most need fixing. citeturn1search15turn4search0turn4search1turn17search1

A realistic migration estimate is **35–60 developer-days** for a thoughtful adaptation, not including later operational work. That buys you durable workflow semantics, but not your Windows process-safety invariant. Temporal is therefore a strategic option, not the immediate answer. citeturn1search15turn4search0turn17search1

### Hatchet

Hatchet is more relevant than many “AI workflow” tools because it explicitly positions itself around background tasks, durable execution, retries, real-time monitoring, task stats, rate limits, and task replay. Its docs describe PostgreSQL as the durable store for queued/running/completed state, and its durable execution material explains replaying work from where it failed. In design *shape*, that is much closer to Foreman than a data pipeline scheduler is. citeturn9search6turn9search8turn9search10turn9search13turn9search15turn9search14

The blocker is environmental fit. Hatchet’s self-hosting guidance today is Docker, Docker Compose, or Kubernetes; its quick local start path wraps a Dockerized “Hatchet Lite,” and the docs explicitly say that deployment requires Docker installed locally. That conflicts with your stated baseline. Even if you accepted the infra cost, Hatchet still would not solve child-process ownership by itself; you would still need the same safe Windows launcher around arbitrary vendor CLIs. That makes Hatchet a sensible Linux-first contender, but a poor Windows-no-Docker replacement for Foreman’s current orchestration layer. citeturn9search5turn9search9turn9search18turn17search1

Migration cost is roughly **25–40 developer-days**, plus operational overhead the in-house path avoids. I would not pursue it for this host class. citeturn9search5turn9search13turn17search1

### Windmill

Windmill is one of the more credible “scripts and flows” platforms for CLI-heavy work because it speaks Bash/PowerShell directly, supports running scripts locally or over SSH, and allows workers to preinstall binaries that can then be executed in subprocesses. If the problem were “I need a nice OSS workflow product for Bash and PowerShell jobs,” Windmill would be more attractive than most orchestration tools. citeturn11search1turn11search7turn11search14

The fit breaks on the exact constraint you emphasized. Windmill’s self-hosted story is Docker or Kubernetes, and its **Windows native workers are a self-hosted Enterprise feature**, not part of the open-source baseline. In other words, Windmill can look Windows-friendly at the worker layer, but the path that actually avoids Docker/WSL on Windows is not the open-source path you asked for. That makes it unsuitable as the recommended OSS replacement for Foreman’s orchestration layer. citeturn11search3turn11search16

If you were willing to change the constraint set—especially if Linux workers or commercial features became acceptable—Windmill would move up the list. Under the current rules, it is a non-finalist. citeturn11search3turn11search16

### LangGraph

LangGraph is the most useful agent-specific framework studied here, but not as a replacement for Foreman’s subprocess orchestration. Its docs are explicit about what it is good at: long-running, stateful agents; checkpointers that save state at each step; thread-scoped persistence; human-in-the-loop; time travel; and fault-tolerant execution. Those are valuable patterns, especially for your event log, checkpoint, and replay machinery. citeturn33search3turn34search0turn34search5turn34search7turn34search19

What LangGraph does **not** provide is first-class OS-process supervision for arbitrary foreign CLIs. You can certainly wrap a subprocess call as a tool or node, but LangGraph’s durability is about **graph state**, not about owning a Windows process tree or enforcing “auditor vendor != implementer vendor” at the process/sandbox boundary. So LangGraph is best treated as a source of design ideas to copy—checkpointers, thread IDs, replay/fork semantics—not as the immediate answer to F1/F2. citeturn34search5turn34search7turn17search1

Adaptation cost depends on scope. If you only borrow concepts and schema ideas, the cost is low. If you try to rebuild Foreman’s entire control plane as a LangGraph app while still wrapping Grok/Codex/Claude CLIs, expect **15–25 developer-days** before you are even parity-close—and you still will not have solved process ownership without a native launcher. citeturn34search5turn34search7turn17search1

### Claude Code primitives

Claude Code is not a general replacement for Foreman, but it is the only agent-specific tool in this survey that ships **serious process/session-management primitives** for its own ecosystem: worktree-native parallel sessions in the CLI, background sessions, an attach/logs/stop/respawn flow, and an explicit session supervisor. Its docs also describe how `claude --worktree` creates isolated worktrees, how non-interactive `-p` mode works with worktrees, and how background sessions are monitored and reattached. That is meaningful proof that some of the behaviors Foreman wants are already “normal” in a modern coding-agent harness. citeturn32view0turn32view1

The catch is scope. These primitives govern **Claude Code sessions**, not arbitrary third-party vendor CLIs. There is also a subtle shared-state issue: automatic project memory lives under `~/.claude/projects/<project>/memory/`, and all worktrees within the same repo share that memory directory unless you redirect it. So for Foreman, Claude Code is a useful source of patterns—explicit worktree isolation, background-session supervision, attach/respawn semantics, project-local state—but not an orchestration replacement. citeturn28search6turn28search10turn32view0turn32view1

## Liveness and state-machine design

Foreman’s current file-activity watchdog is too coarse because it tries to infer process liveness from one signal: worktree writes. Mature CI systems use **multiple channels**. Buildkite agents send heartbeats, and if the API receives no heartbeat for **three consecutive minutes**, the agent is marked lost within the next **60 seconds**. Buildkite also gives canceled or timed-out jobs a default **10-second cancel grace period** before forcing termination. GitHub Actions distinguishes long-running background work from ordinary steps with explicit `background`, `wait`, and `wait-all` semantics, instead of inferring “done” from silence, while also exposing a very large default job timeout of **360 minutes**. GitLab Runner has recently added stage-specific controls such as `prepare_timeout` and `get_sources_timeout`, with its `boot_verify` canary defaulting to **5 minutes**, plus `1s`/`10s` acquire backoff defaults. citeturn23search5turn23search1turn20search0turn26view0

For Foreman, the transferable pattern is a **typed lane state machine**, not “mtime plus vibes.” I recommend these states: `QUEUED`, `STARTING`, `RUNNING_IMPL`, `RUNNING_AUDIT`, `VERIFYING`, `WAITING_CHILD`, `STALLED`, `DEAD`, `SUCCEEDED`, and `FAILED`. `WAITING_CHILD` should exist specifically to kill F2: a wrapper is not allowed to transition to any terminal state unless the native launcher reports child exit and the required report artifact is present. The launcher should emit a heartbeat event every **15–30 seconds** carrying PID, Job ID, exit code if known, cumulative stdout/stderr byte counters, and a phase enum reported by the wrapper (`implement`, `audit`, `verify`, `report-write`). The orchestrator should compute stall from **heartbeats plus phase**, not from file writes. citeturn17search1turn16view0turn23search5turn20search0turn26view0

A good first set of thresholds is conservative and phase-aware: `STARTING` stale after **90 seconds** with no child registered; `RUNNING_IMPL` stale after **5 minutes** with no heartbeat; `RUNNING_AUDIT` stale after **15 minutes**; `VERIFYING` stale after **10 minutes**; hard lane timeout per task class; then a **10-second** graceful cancel period before job-close kill, borrowing Buildkite’s default as a sensible starting point. This is an engineering recommendation rather than a vendor default: the exact numbers should be tuned from your own traces, but the principle should not be compromised—**queued is not running, verifying is not stalled, and silence is not enough to classify a lane**. citeturn23search1turn23search5turn26view0

## Vendor CLI concurrency findings

The strongest official evidence of native multi-session parallelism is on the **Claude Code** side. Anthropic documents parallel sessions with worktrees in the CLI, says each session can run in its own worktree, and exposes a background-session supervisor with commands such as `claude agents`, `claude attach`, `claude daemon status`, `claude stop`, and `claude respawn`. That is a meaningful sign that Anthropic expects concurrent agent activity on one machine. The main caveat for Foreman is that Claude stores auto memory per project path under `~/.claude/projects/<project>/memory/`, and all worktrees of the same repo share that directory by default, so lane isolation may require redirecting memory or separating repos more aggressively than your current worktree-only scheme. citeturn32view0turn32view1turn28search6turn28search10

For **xAI Grok Build**, the picture is more ambiguous but still useful. xAI’s own launch post explicitly advertises “subagents that work in parallel” and worktree integrations, while the docs expose `GROK_HOME` and describe a layered config model rooted in `~/.grok` or `$GROK_HOME`. That means per-lane config and session isolation is supported mechanically even if I did **not** find official guidance that says, plainly, “run N independent Grok CLI instances concurrently on one Windows host.” I would treat the per-lane `GROK_HOME` workaround as **supported by the path model but UNVERIFIED as a concurrency remedy**. In practice, that means: unique `GROK_HOME` per lane, unique log/session dirs, and a pueue concurrency group of **1** for xAI until destructive tests prove higher values are safe. citeturn27search0turn30search6turn30search8turn30search0

For **Codex CLI**, OpenAI’s official docs clearly support `CODEX_HOME` for local state isolation and position the CLI for scripted/CI use. The Codex app is explicitly marketed as a place to run multiple agents in parallel, but that is app-level evidence, not a guarantee about many independent local CLI instances sharing one host, one account, or one workspace. I did not find official CLI guidance promising safe high-parallel local invocation. So the sound posture is similar to Grok Build: use a distinct `CODEX_HOME` per lane, prefer a stable auth mode, and treat high parallelism as **UNVERIFIED** until tested. If you need guaranteed concurrency sooner, bias Claude lanes upward first, then Codex, then Grok. citeturn31view0turn31view1turn29search1

Ranked by operational risk, the best workarounds are: **lowest risk**—per-lane config/state dirs (`GROK_HOME`, `CODEX_HOME`, redirected Claude memory/settings where needed); **medium risk**—per-vendor queue caps enforced outside the CLI; **highest risk**—assuming git worktrees alone imply vendor-CLI concurrency. F3 strongly suggests they do not. citeturn30search6turn30search8turn31view0turn32view0turn16view0

## Merge freshness and event-log design

For F6, the right fix is not primarily a new VCS; it is a **freshness gate**. GitHub’s required status checks can enforce that branches are up to date before merge, and GitHub’s merge queue goes further by validating each pull request against the **latest** target branch plus whatever is ahead of it in the queue. That is directly transferable to Foreman. Every remote lane should record its **dispatch merge-base** at start, re-check it before final verification, and fail fast if the lane no longer has the required ancestry relationship. If the ancestry is gone entirely—as in your 55-commit no-common-ancestor branch—the orchestrator should mark the lane non-mergeable and respawn from a fresh base rather than attempt salvage automation. citeturn40search18turn40search2turn40search0turn40search6

Your current `events.jsonl + refs/checkpoints/*` direction is conceptually sound, and the best outside ideas to copy are from **LangGraph checkpointers** and **Codex local history compaction**. LangGraph saves graph state as checkpoints at each step, organizes them into threads, and supports replay/fork from prior checkpoints without re-executing earlier saved work. Codex’s config docs describe transcript persistence under `CODEX_HOME`, optional disabling of persistence, and file-size-based history compaction. The practical lesson for Foreman is that your event log should distinguish at least four entities: **run**, **lane**, **attempt**, and **checkpoint**. Each event should carry a monotonic sequence number, run/lane/attempt IDs, state transition, child PID + Job ID, worktree path, config-dir path, merge-base hash, vendor session identifier if available, and optional checkpoint ref. Then add **cursor semantics**: the ability to replay from “all events after attempt X checkpoint Y.” citeturn34search5turn34search7turn31view0

The schema deltas I would adopt before the design ossifies are simple but important. First, record **phase-specific heartbeats** as first-class events, not as inferred state. Second, record **ownership**: which launcher/Job Object created which child, in which worktree, under which config dir. Third, record **merge-base and base-ref freshness** both at dispatch and at pre-merge validation. Fourth, support **event-log compaction of non-structural chatter** while keeping structural milestones immutable. The event stream should be append-only, but not every byte needs to be forever. That is the same separation mature durable systems make between state checkpoints and raw conversational/log detail. citeturn34search5turn31view0

## Recommendation, migration costs, and source list

The evidence-based call is:

**Recommended path: keep building Foreman in-house, but adopt targeted primitives immediately.**

Concretely, that means:
- **Adopt** a native Windows lane launcher built on Job Objects.
- **Adopt** pueue for per-vendor queues, persisted task control, and JSON-visible lane status.
- **Adapt** Foreman’s event log/checkpoint design to mimic durable-execution best practices from LangGraph and similar systems.
- **Defer** Prefect unless you decide to move the control plane into Python within the next quarter.
- **Defer** Temporal unless Foreman becomes a multi-host platform with a larger operator budget.

That recommendation is not conservative for its own sake. It is the only path that attacks the actual root cause of F1 and F2 without first dragging the system into a new architecture that still needs the same launcher. citeturn17search1turn17search3turn16view0turn13search10turn34search5

A realistic migration-cost view for one developer is:

| Option | Estimate | What you are really paying for |
|---|---:|---|
| Harden Foreman in place | **12–18 dev-days** | Native launcher, pueue integration, typed events, heartbeats, resume cursors, destructive testing |
| Adapt Prefect | **20–35 dev-days** | Python control plane, workers/work pools, UI/state mapping, plus the same native launcher |
| Adapt Temporal | **35–60 dev-days** | New workflow model, service deployment, worker/activity plumbing, history/replay semantics, plus the same native launcher |
| Adapt Hatchet | **25–40 dev-days** | Docker/Postgres control plane, durable tasks integration, plus native launcher |
| Adapt LangGraph as core | **15–25 dev-days** | Durable graph state and replay semantics, but still no generic process-tree ownership |

The best 30/60/90-day plan is straightforward. In the first 30 days, build and ship the Windows launcher, replace Bash-owned timeouts, add explicit lane states, and put all xAI/Codex lanes behind pueue groups with deliberately conservative concurrency caps. By day 60, complete checkpoint-and-resume from git refs plus event cursors, add merge-base freshness gates, and make vendor config-dir isolation mandatory. By day 90, decide whether Foreman still wants a richer operator API/UI; if yes, prototype **Prefect around the hardened launcher**, not instead of it. If no, keep the event-log architecture and continue iterating as a single-host durable harness. citeturn17search1turn16view0turn40search0turn40search18turn13search10
