# 2026-08-02

## Session: Council study, graphify, and what it exposes about the review loop

Kept as a running log of issues and enhancements while evaluating the Council
component as a review plane for the grok-4.5 lanes finishing v0.2.9.0.

### 1. What actually happened, in order

Council arrived as `release/v0.3.0-council` — a git subtree at
`components/council/`, 101 files, plus three lane branches and worktrees. It is
a local-first cross-provider deliberation plugin in TypeScript with Effect 3:
independent sealed proposals, blinded candidates, non-author judges, evidence
tracking, typed abstention. Its own gate is green — **114 tests in 9 files**,
strict OpenSpec valid — but only `packages/schema` and `packages/domain` exist.
Provider adapters, Effect application services, research tools, the MCP server
and the host plugins are all unimplemented.

Graphified it: 864 nodes, 917 edges, 75 communities from 84 files.

Reading its deliberation spec against the review loop I have been running all
session was the useful part, because the spec names — as requirements — four
things my loop does not do, and three of them correspond to failures I actually
hit today.

### 2. What went right

| Claim | Evidence |
|---|---|
| Council's own gate is real | `corepack pnpm verify` → 114 tests, 9 files, OpenSpec `design-council-core` valid |
| The graph builds without an LLM or API cost | `graphify update .` → 864 nodes / 917 edges / 75 communities, 0 input tokens, 0 output tokens |
| The deliberation spec is specific enough to implement against | Every requirement is a SHALL/MUST with a named failure mode, not a principle |

### 3. What went wrong

| What it claimed | What was true |
|---|---|
| `graphify update --no-viz` | `--no-viz` is documented under `cluster-only`, rejected by `update`. Flag exists in the help text one command away from where it works |
| Running `graphify update .` in a component is harmless | It writes `graphify-out/` into `components/council/`, which is in neither `.prettierignore` nor `.gitignore`, and **broke Council's own verify gate** — 60 prettier failures on generated files |
| Council needed graphifying | It already ships a graph at `docs/research/graphify/`. The default output path created a **second, competing** graph location in a repo whose whole doctrine is one canonical record |
| The auditor sees the round's change | It sees **cumulative uncommitted worktree state**. Round-3 finding 3 flagged `foreman-cleanup.sh` as out-of-scope; it is round-1's task-3 wiring, uncommitted because the lane has not merged |
| The auditor sees current dependency records | The lane worktree sat at `3eb6af6` while the release branch was at `d5501ad`. `jq` **was** promoted to `must` on every profile; the auditor read the stale copy and filed it as a HIGH finding |
| A verdict is a verdict | Of three HIGH findings in round 3, one was real, one was false, one was misattributed. The false and misattributed ones share a single cause: **I never synced the lane worktree after committing** |

Two graphify diagnostics worth reporting upstream: the skill-version warning
(`0.9.15` vs package `0.9.32`) prints **twice per invocation**, and four source
files produced zero nodes and are silently absent from the graph
(`SOURCES.json` ×3, `graph.json`).

### 4. Standing rules that came out of today

- **Sync the lane worktree to the release branch before every audit round.**
  Two of three HIGH findings in one round were artifacts of a stale base. An
  auditor reading old dependency records will file correct-looking findings
  about fixed problems, and there is no way to tell from the verdict.
- **Give the auditor the round's diff, not the worktree.** Cumulative state
  makes carry-over indistinguishable from a scope violation.
- **A generated index belongs where its project already puts it.** `graphify
  update .` defaulting to `./graphify-out` created a second graph in a component
  that already had one, and broke its gate on the way.
- **Council's quorum requirement is the one my loop most clearly fails.** It
  demands at least three admissible proposals from at least two independent
  failure domains, and states that raw worker count MUST NOT satisfy diversity.
  My review loop is one auditor from one family.

### 5. Where things stand

Council is studied, graphified and understood. It is **not runnable as a review
plane today** — no provider adapters — so it cannot review the grok lanes yet.
The plan written alongside this entry covers what to build to get there and what
to adopt immediately without building anything.

The fit-report lane is on round 3 with one genuine defect outstanding: two JSON
objects on a single NDJSON line count as zero rather than refusing.
